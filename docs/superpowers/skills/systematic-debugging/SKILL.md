# Systematic Debugging（系统化调试）

## 概述

系统化调试是一套结构化的问题解决流程，而不是随机尝试。它基于一个简单原则：你解决的问题越多，下次解决问题就越快。

## 4 阶段根因分析

```
┌────────────────────────────────────────────────────────────┐
│  1. 复现问题                                               │
│  找到最小复现步骤，记录错误信息                              │
└────────────────────────────────────────────────────────────┘
                          ↓
┌────────────────────────────────────────────────────────────┐
│  2. 收集证据                                               │
│  查看日志、错误堆栈、输入输出                                │
└────────────────────────────────────────────────────────────┘
                          ↓
┌────────────────────────────────────────────────────────────┐
│  3. 追踪根因                                               │
│  从症状到原因反向追踪                                       │
└────────────────────────────────────────────────────────────┘
                          ↓
┌────────────────────────────────────────────────────────────┐
│  4. 验证修复                                               │
│  确认问题已解决，确认没有引入新问题                          │
└────────────────────────────────────────────────────────────┘
```

## 阶段 1：复现问题

### 目标
找到**最小复现步骤**——引发问题所需的最少操作。

### 方法
1. **隔离变量**：什么变了？最近部署？新功能？配置变更？
2. **简化场景**：能否用更简单的输入复现？
3. **记录环境**：操作系统、版本、时间、相关数据状态

### 最小复现原则
- 如果不能可靠复现，就不能验证修复
- 最小复现 > 完整场景（更快、更清晰）

### 输出
```
问题：[简要描述]
触发步骤：
1. [步骤1]
2. [步骤2]
...
环境：[相关上下文]
预期行为：[应该发生什么]
实际行为：[实际发生什么]
```

## 阶段 2：收集证据

### 日志分析
```bash
# 查看最近错误
tail -100 logs/error-*.log | grep -A5 "ERROR"

# 搜索特定错误
grep -r "SpecificErrorMessage" logs/

# 查看时间范围内的日志
grep "2026-06-04 17:3" logs/app-*.log
```

### 错误堆栈分析
1. 从底部开始（根本原因通常在底部）
2. 找第一行业务代码（不是框架代码）
3. 追踪调用链

### 输入输出验证
- 打印关键变量值
- 验证数据格式
- 检查边界条件

## 阶段 3：追踪根因

### 追踪技术

#### 二分查找
```
如果问题在 A-Z：
- 测试 M 点
- 问题在 M 之前？测试 G
- 问题在 M 之后？测试 T
- 持续二分直到定位
```

#### 控制变量法
```javascript
// 假设：问题由 X 引起
// 验证：保持其他所有变量不变，只改变 X
// 如果问题消失/出现 → X 是原因/部分原因
```

#### 假设-验证循环
```
1. 提出假设："可能是 X 导致的"
2. 设计验证："如果我这样做，会看到 Y"
3. 执行验证
4. 根据结果验证/推翻假设
```

### 防御深度（Defense in Depth）

当你怀疑多个可能原因时：
```
层 1: 最可能的原因 → 验证/排除
层 2: 次可能的原因 → 验证/排除
层 3: ... 继续直到找到根因
```

### 条件等待（Condition-Based Waiting）

对于竞态条件或异步问题：
```javascript
// 坏：固定延迟
await new Promise(r => setTimeout(r, 5000));

// 好：条件等待
await waitFor(
  () => condition === expected,
  { timeout: 5000, interval: 100 }
);
```

## 阶段 4：验证修复

### 验证清单
- [ ] 原始问题已解决
- [ ] 相关功能未受影响
- [ ] 没有引入新的边缘情况
- [ ] 日志干净（无错误）
- [ ] 性能未显著下降

### 回归测试
修复后运行相关测试套件：
```bash
# 运行相关测试
npm test -- --testPathPattern="related-feature"

# 运行完整测试套件
npm test
```

## 常见 Bug 模式

| 症状 | 可能原因 | 检查方法 |
|------|----------|----------|
| 间歇性失败 | 竞态条件、缓存问题 | 检查异步代码、添加日志 |
| 性能逐渐下降 | 内存泄漏、资源未释放 | 检查连接池、事件监听器 |
| 特定用户失败 | 权限、状态、数据问题 | 检查用户数据、权限配置 |
| 部署后失败 | 环境差异、配置问题 | 对比环境变量、版本差异 |
| 高并发失败 | 并发问题、资源竞争 | 检查锁、连接池、队列 |

## 调试工具

### Node.js
```javascript
// 添加调试日志
console.log('[DEBUG] variable:', variable);

// 使用 util.inspect 查看复杂对象
const util = require('util');
console.log(util.inspect(obj, { depth: null }));

// 检查内存使用
console.log(process.memoryUsage());
```

### 日志追踪
```javascript
// 添加请求 ID 方便追踪
const requestId = generateRequestId();
logger.info({ requestId, event: '开始处理' });
// ... 中间逻辑 ...
logger.info({ requestId, event: '处理完成' });
```

## 最终规则

> **每个 bug 都需要一个测试。** 修复后添加回归测试，确保问题不会再次出现。

如果找不到 bug，添加更多日志来缩小范围。

如果 bug 消失又出现，这是间歇性 bug。收集更多证据直到找到根因。
