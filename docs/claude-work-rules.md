# Claude Code 工作规范

> 每次执行任务前必须阅读此文档

---

## 🎯 核心原则

**AI-Guardrails 模式**

```
你给目标    →    我分析      →    你确认范围
    ↓                           ↓
写规格      →    你确认规格    →    我实现
    ↓                           ↓
写测试      →    我自审        →    跑测试
    ↓                           ↓
你验证      ←    全部通过
```

---

## 1️⃣ 六大安全策略

### 策略 1：TDD 约束（测试驱动）

**要求：** 先写测试用例覆盖当前行为，然后再优化。测试必须通过才算完成。

**执行：**
- 先理解"什么行为不能破坏"
- 改完后运行测试验证
- 测试覆盖意图路由、工具调用、API端点

### 策略 2：功能规格文档化

**要求：** 先输出规格，再实现。

**输出内容：**
1. 这个功能做什么
2. 输入/输出是什么
3. 边界情况处理
4. 成功/失败场景

**流程：**
1. 先写《功能规格文档.md》
2. 你确认后再实现
3. 实现完后对照文档检查

### 策略 3：代码审查机制

**要求：** 自己审查自己的代码。

**必须包含：**
1. 列出改了什么
2. 说出潜在的失败点
3. 自己觉得哪里可能出问题

### 策略 4：渐进式 + 验证

**要求：** 小步快跑，不要一次性大改。

**执行：**
- 一次只改一个模块/一个功能
- 改完运行测试，确认通过后再进行下一步
- 不要"顺便改一下其他东西"

### 策略 5：真实功能验证（最重要！）

**要求：** 防止"外壳"功能，必须端到端验证。

```javascript
async function test_real_functionality() {
  // 测试实际场景，不是mock数据
  const result = await actualSearch("用户真实会搜的词");
  if (!result) throw new Error("功能没有真正工作");
  
  // 边界情况
  const edge = await actualSearch("");
  // 验证返回了合理的结果
  
  // 错误处理
  const error = await actualSearch(null);
  // 验证不会崩溃
}
```

### 策略 6：端到端验证脚本

**要求：** 写一个 e2e-test.js，包含用户真实使用场景。

**验证：**
- 前端 → API → 后端逻辑 → 返回结果
- 不允许只加UI不加后端
- 不允许只加路由不加实现

## 2️⃣ 功能模块单一化

**原则：** 拒绝文件代码拥挤繁重，保持每个模块职责清晰。

**执行：**
- 一个文件只做一件事
- 单个文件代码行数不超过 300 行（超出则拆分）
- 按功能/职责划分目录结构
- 避免"大杂烩"文件（如 utils.js 包含几百个无关函数）

**拆分信号：**
- 文件超过 300 行
- 文件有多个不相关的功能
- 同一个功能分散在多个文件中（难以定位）
- 改动一个功能需要同时改多个文件

| 有哪些现有测试不能破坏？ | ? |
| 这个功能怎么手动验证？ | ? |

---

## 4️⃣ 自动化检查

**健康检查脚本：**
- 启动时自动检查所有API端点是否可用
- 前端页面加载时检查关键功能是否正常
- 发现问题自动回退或提示

**测试执行：**
- 每次修改后自动跑测试
- 改坏了立刻知道
- 有测试的代码才能改

---

## ⚠️ 关键禁止事项

| 禁止 | 说明 |
|------|------|
| 没测试就改代码 | 必须先写测试或确认有测试覆盖 |
| 没确认规格就实现 | 必须先输出规格并获得确认 |
| 一次性大改 | 一次只改一个模块 |
| 假功能 | 必须端到端验证，不允许空壳 |
| 文件过度膨胀 | 单文件不超过 300 行 |
| 混合职责文件 | 一个文件只做一件事 |
