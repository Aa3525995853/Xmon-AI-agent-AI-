# Brainstorming（头脑风暴）

将想法通过自然协作对话转化为完整的设计和规范。

从了解当前项目上下文开始，然后一次问一个问题来细化想法。一旦理解要构建什么，展示设计并获得用户批准。

## 铁律

> **在展示设计并获得用户批准之前，不得调用任何实现技能、编写任何代码、搭建任何项目或采取任何实现行动。** 这适用于每个项目，无论其感知简单性如何。

## 反模式：这样想就错了

> "这太简单了，不需要设计"

每个项目都要经过这个流程待办清单、一个单功能工具、一个配置变更——都是。"简单"的项目正是未经审视的假设造成最大浪费的地方。设计可以很短（对于真正简单的项目，几句话就够了），但你必须展示它并获得批准。

## 检查清单

对于以下每个项目，你必须创建一个任务并按顺序完成：

1. **探索项目上下文** — 检查文件、文档、最近的提交
2. **提供视觉辅助**（如果主题涉及视觉问题）— 这是一条独立消息，不与其他内容合并
3. **提出澄清问题** — 一次一个，理解目的/约束/成功标准
4. **提出 2-3 个方案** — 包括权衡和你的推荐
5. **分块展示设计** — 根据复杂度缩放，每块后获得用户批准
6. **编写设计文档** — 保存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并提交
7. **规范自检** — 快速检查占位符、矛盾、歧义、范围（见下文）
8. **用户审核书面规范** — 在继续之前让用户审核规范文件
9. **过渡到实现** — 调用 writing-plans 技能创建实现计划

## 流程图

```
开始 → 探索项目上下文 → 需要视觉问题?
                                    ↓是               ↓否
                              提供视觉辅助        提出澄清问题
                                    ↓                    ↓
                              提出澄清问题 ←←←←←←←←←←←←←
                                    ↓
                              提出 2-3 个方案
                                    ↓
                              分块展示设计 → 用户批准? → 否 → 修订设计
                                    ↓是                    ↓
                              编写设计文档 → 规范自检 → 用户审核?
                                                                  ↓是
                                                            调用 writing-plans
```

## 关键原则

- **一次一个问题** — 不要用多个问题淹没用户
- **多选题优先** — 比开放式更容易回答
- **YAGNI 严格** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在确定之前始终提出 2-3 个方案
- **增量验证** — 展示设计，获得批准后再继续
- **灵活变通** — 当某些内容不合理时返回澄清

保存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
- （用户对规范位置的偏好优先于此默认值）

## 设计后

**文档：**
- 将验证的设计（规范）写入 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
- 提交设计文档到 git

**规范自审：**
写完规范文档后，用新眼光审视：

1. **占位符扫描：** 是否有 "TBD"、"TODO"、不完整部分或模糊需求？修复它们。
2. **内部一致性：** 各部分是否相互矛盾？架构是否与功能描述匹配？
3. **范围检查：** 这是否足够集中于单一实现计划，还是需要分解？
4. **歧义检查：** 是否有任何需求可以有两种解释？如果是，选择一个并明确。

立即修复任何问题。不需要重新审核——修复后继续。

**用户审核门：**
规范审核循环通过后，在继续之前让用户审核书面规范：

> "规范已写好并提交到 `<path>`。请审核，如果想在开始编写实现计划之前做任何更改，请告诉我。"

等待用户响应。如果他们请求更改，进行更改并重新运行规范审核循环。只有在用户批准后才能继续。

**实现：**
- 调用 writing-plans 技能创建详细实现计划
- 不要调用任何其他技能。writing-plans 是下一步。
