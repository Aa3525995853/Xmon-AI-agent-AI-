# 项目开发规则
服务端与客户端必须分离
不要造成安全风险隐患是第一原则

## 核心原则：每个功能必须端到端可用，禁止空壳
所有功能代码后面必须添加详细注释！！！！

代码编写规范

### 3.1 命名规范
| 类型 | 规范 | 示例 |
|------|------|------|
| 文件名 | 小写+下划线 (snake_case) 或 驼峰 (camelCase)，保持项目统一 | `user_service.py` / `userService.js` |
| 类名 | 大驼峰 (PascalCase) | `UserService`, `DataProcessor` |
| 函数/方法名 | 小驼峰 (camelCase) 或 下划线 (snake_case) | `getUserInfo()`, `get_user_info()` |
| 变量名 | 有意义、可读性强的名称，禁止用 a, b, c, tmp1 | `user_name`, `order_list` |
| 常量 | 全大写+下划线 | `MAX_RETRY_COUNT`, `API_BASE_URL` |

### 3.2 函数规范
- 每个函数**只做一件事**（单一职责原则）
- 单个函数体不超过 **50 行**，超过则拆分为子函数
- 参数不超过 **5 个**，超过则用对象/字典封装
- 必须有返回值说明

### 3.3 错误处理
- 关键操作必须有 try-catch / try-except
- 错误日志要包含：时间、模块名、错误信息
- 禁止使用空的 catch/except（吞掉异常）

---

## 四、注释规范（重点！）

### 4.1 文件头部注释（每个文件必须有）
```
/**
 * @file 文件名
 * @description 文件的整体功能描述
 * @module 所属模块名
 * @author 作者
 * @version 版本号
 * @date 创建/修改日期
 */
```

### 4.2 函数/方法注释（每个公开函数必须有）
```
/**
 * @description 函数功能描述
 * @param {类型} 参数名 - 参数说明
 * @param {类型} 参数名 - 参数说明
 * @returns {类型} 返回值说明
 * @throws {异常类型} 异常说明（如有）
 * @example 使用示例（关键函数需要提供）
 */
```

### 4.3 行内注释
- 复杂逻辑处必须添加行内注释，解释**为什么**这么做（而非做了什么）
- 魔法数字必须用常量替代并注释
- 禁止无意义注释，如：`i++ // i加1`

### 4.4 模块分割注释
```
// ============================================================
// 模块名称：用户认证模块
// 功能说明：处理用户登录、注册、Token刷新等功能
// ============================================================
```

## 规则1：先验证后端，再写前端

**禁止**：先写UI/前端代码，后补后端逻辑。

**必须**：
1. 先确认后端API存在且能正常返回数据
2. 用 `curl` 或脚本实际调用API验证返回值
3. 后端验证通过后，再写前端代码

**反面案例**：加了Excel预览UI，但 `/api/system/preview-excel` 接口还没写。

---

## 规则2：改路由前，先验证目标处理器

**禁止**：修改 intentRouter 路由目标，但不验证目标处理器能否处理。

**必须**：
1. 修改路由前，先检查目标处理器的代码
2. 确认目标处理器有对应的方法/逻辑
3. 如果目标处理器缺失方法，先补方法再改路由

**反面案例**：把 data_analysis 路由从 chat 改到 task，但 taskOrchestrator 用 Kimi 效果差。

---

## 规则3：每次修改后必须运行验证脚本

**必须**：每次代码修改后，运行 `node scripts/verify.js` 验证：
- 所有API端点返回正常（非500）
- 核心服务方法存在
- 前端页面可加载

**如果验证失败**：必须先修复验证失败项，再做其他修改。

---

## 规则4：一次只改一个链路

**禁止**：同时修改前端+后端+路由+提示词。

**必须**：
1. 每次只修改一个完整链路（前端→API→后端→返回）
2. 修改后立即验证该链路
3. 验证通过后再改下一个

---

## 规则5：添加API路由时，必须同时实现底层方法

**禁止**：只添加路由 `router.get('/xxx')` 但底层服务方法不存在。

**必须**：
1. 添加路由前，先确认服务层方法存在
2. 如果方法不存在，先实现方法
3. 方法实现后，用脚本验证路由能正常返回

**反面案例**：添加了 `/api/task/grouped` 路由，但 `getTasksGrouped()` 方法不存在。

---

## 规则6：不引入被墙的外部资源

**禁止**：使用 `fonts.googleapis.com`、`ajax.googleapis.com` 等国内无法访问的CDN。

**允许**：
- `fonts.loli.net`（Google Fonts国内镜像）
- `cdn.jsdelivr.net`
- `cdnjs.cloudflare.com`
- 本地资源

---

## 规则7：修改提示词后，必须检查完整调用链

**禁止**：修改 MimoProvider 提示词但不检查工具定义是否匹配。

**必须**：
1. 修改提示词中提到的工具名，必须在 `getToolDefinitions()` 中存在
2. 提示词中的代码示例必须与工具描述一致
3. 提示词要求的功能必须有对应的工具实现

---

## 规则8：功能完成的定义（Definition of Done）

一个功能"完成"必须满足：
1. ✅ 后端API返回正确数据（不是500/404）
2. ✅ 前端能正确展示数据（不是空白/报错）
3. ✅ `node scripts/verify.js` 验证通过
4. ✅ 没有引入新的console错误
5. ✅ 没有破坏已有功能

**缺少任何一项 = 未完成**

---

## 规则9：禁止"待实现"占位符

**禁止**：写 `return { info: '待实现' }` 或 `// TODO: 待实现` 的占位代码。

**必须**：要么实现完整功能，要么不添加这个路由/方法。

---

## 规则10：修改前必须先读取当前代码

**禁止**：凭记忆修改代码，不先读取当前文件内容。

**必须**：
1. 修改任何文件前，先用 Read 工具读取当前内容
2. 确认要修改的代码确实存在
3. 确认修改不会与现有逻辑冲突
