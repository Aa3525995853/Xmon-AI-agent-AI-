# Requesting Code Review（请求代码审查）

在问题级联之前分派代码审查子代理来捕捉问题。审查者获得精确制作的上下文进行评估——绝不是你的会话历史。这让审查者专注于工作产品，而不是你的思维过程，并保留你自己的上下文继续工作。

**核心原则：** 早审查，常审查。

## 何时请求审查

**必须执行：**
- 子代理驱动开发中每个任务之后
- 完成主要功能后
- 合并到 main 之前

**可选但有价值：**
- 卡住时（全新视角）
- 重构前（基线检查）
- 修复复杂 bug 后

## 如何请求

**1. 获取 git SHAs：**
```bash
BASE_SHA=$(git rev-parse HEAD~1)  # 或 origin/main
HEAD_SHA=$(git rev-parse HEAD)
```

**2. 分派代码审查子代理：**

使用 Task 工具，填写审查模板（见下方）。

**占位符：**
- `{DESCRIPTION}` - 你构建的内容的简要总结
- `{PLAN_OR_REQUIREMENTS}` - 它应该做什么
- `{BASE_SHA}` - 起始提交
- `{HEAD_SHA}` - 结束提交

**3. 处理反馈：**
- 立即修复严重问题
- 继续之前修复重要问题
- 将较小问题记下稍后处理
- 如果审查者错了，推回去（附上理由）

## 审查清单

### 🔴 严重问题（阻塞）
- [ ] 安全性问题（SQL注入、XSS、密码明文等）
- [ ] 内存泄漏风险
- [ ] 关键路径错误处理缺失
- [ ] 业务逻辑错误

### 🟡 中等问题
- [ ] 代码重复（DRY违反）
- [ ] 命名不规范
- [ ] 缺少注释的关键逻辑
- [ ] 性能问题（N+1查询等）

### 🟢 建议优化
- [ ] 代码风格
- [ ] 错误信息不够清晰
- [ ] 可以简化的逻辑

## 审查报告格式

```markdown
## 代码审查报告

**任务：** [任务名称]
**审查者：** [审查者名称]
**日期：** [日期]

### 🔴 严重问题
| 文件:行号 | 问题描述 | 影响 | 建议 |
|-----------|----------|------|------|
| src/xxx.js:45 | 描述 | 影响 | 建议 |

### 🟡 中等问题
| 文件:行号 | 问题描述 | 建议 |
|-----------|----------|------|
| src/xxx.js:67 | 描述 | 建议 |

### 🟢 建议
| 文件:行号 | 建议 |
|-----------|------|
| src/xxx.js:89 | 建议 |

### 总体评估
- [ ] 可以继续
- [ ] 需要修复后继续
- [ ] 需要重新设计
```

## 红线

**永远不要：**
- 因为"很简单"跳过审查
- 忽略严重问题
- 有未修复的重要问题继续
- 与有效技术反馈争论

**如果审查者错了：**
- 用技术推理推回去
- 展示证明它有效的代码/测试
- 请求澄清

## 与工作流集成

**子代理驱动开发：**
- 每个任务后审查
- 在问题级联之前捕捉
- 修复后再继续下一个任务

**执行计划：**
- 每个任务后或自然检查点审查
- 获得反馈，应用，继续

**临时开发：**
- 合并前审查
- 卡住时审查
