# 严格完成度测试与评分标准

> 目的：以后评估项目完成度时，只按“用户实际操作是否真的完成”打分。代码存在、路由存在、构建通过、mock 测试通过，都不能直接算功能完成。

## 评分结论口径

完成度使用百分制，但必须先说明评估口径：

- **真实可用完成度**：默认使用这个分数。按用户点击/输入后是否真实产生结果计算。
- **工程骨架完成度**：只反映代码结构、页面、路由、测试脚本是否存在，不能当作产品完成度。
- **本地演示完成度**：允许 mock 或本地假数据，但必须明确标注，不得混入真实可用完成度。

最终对外只报 **真实可用完成度**，除非用户明确要求看工程骨架。

## 总分权重

| 维度 | 权重 | 合格标准 |
|---|---:|---|
| 用户主流程闭环 | 30 | 从前端操作到后端处理再到 UI 展示真实结果，不能只显示“已完成” |
| 功能真实实现 | 25 | 不依赖 mock、待实现、空返回、假成功、固定示例数据 |
| 外部依赖可用性 | 15 | LLM/TTS/ASR/搜索/系统自动化等依赖能真实调用，并有配置检查 |
| 失败反馈与可观测性 | 10 | 失败要在 UI 和日志中明确显示原因，不允许静默失败 |
| 测试可信度 | 10 | 测真实 server、真实路由、真实服务边界，不用自建假 app 冒充 E2E |
| 部署与运行一致性 | 5 | Docker/PM2/dev/prod 路径与 monorepo 实际结构一致 |
| 项目整洁度 | 5 | 运行产物、日志、上传文件、密钥、乱码文档不污染源码判断 |

## 强制检查清单

每次评分前必须执行或人工核验：

1. **前端入口追踪**
   - 扫描 `fetch(`、`axios`、`WebSocket`、`socket.on`。
   - 对每个按钮/菜单/面板确认是否调用真实 API。
   - 任何只改前端状态、不调用后端的功能，最高按 20% 计。

2. **后端接口追踪**
   - 对前端调用的每个 `/api/*` 找到真实 route/controller/service。
   - 看到 `success: true`、`completed`、`ok: true` 必须继续追到实际副作用。
   - 如果只是返回“操作完成”“已排队”“已提交”，但没有真实执行结果，不能算完成。

3. **mock/占位扫描**
   - 必扫关键词：
     - `mock`
     - `stub`
     - `dummy`
     - `placeholder`
     - `TODO`
     - `FIXME`
     - `待实现`
     - `暂时`
     - `即将上线`
     - `模拟`
     - `return Buffer.from('')`
   - 命中后必须判断是否在生产路径中。
   - 生产路径命中 mock 或待实现，相关功能最高按 10% 计。

4. **真实依赖检查**
   - TTS/ASR/LLM/搜索/API key 缺失时，不能按可用计算。
   - `isAvailable()` 只检查配置、不真实调用外部服务时，不能作为可用证据。
   - 默认 provider 是 `mock` 的模块，默认状态按不可用计算。

5. **测试可信度检查**
   - E2E 必须加载真实 app/server 或通过真实运行服务访问接口。
   - 自建 Express app、自建 mock route、自建 mock data 的测试，只能算单元/契约草稿，不能算 E2E。
   - 测试环境强制 `TTS_PROVIDER=mock`、mock LLM、mock auth 时，必须单独扣分。

6. **结果回显检查**
   - 后端返回的真实 `result/filePath/downloadUrl/error` 必须显示给用户。
   - 前端如果把结果覆盖成 `任务已完成` 这类泛化文本，按“结果未闭环”扣分。

7. **失败路径检查**
   - 断网、API key 缺失、TTS 不可用、工作 Agent 不可用时，UI 必须明确显示失败原因。
   - 静默 catch、console-only、吞掉错误、继续显示成功，都按严重问题处理。

## 单功能评分规则

每个功能按 0-100 打分：

| 分数 | 含义 |
|---:|---|
| 0 | 没入口或完全不可用 |
| 5 | 有 UI/路由，但直接待实现、mock、空返回 |
| 10 | 有部分代码，但生产路径默认 mock 或假成功 |
| 20 | 能触发后端，但没有真实副作用或真实结果 |
| 35 | 有真实实现雏形，但依赖配置/错误处理/回显明显不完整 |
| 50 | 主路径偶尔可用，但失败路径差，测试不足 |
| 70 | 主路径稳定可用，有基本错误反馈和真实测试 |
| 85 | 多场景可用，有真实 E2E、日志、部署一致 |
| 95 | 接近生产级，有边界测试、监控、恢复机制 |

项目总分不能简单平均，按用户最核心功能加权。

## 一票降级规则

出现以下任一情况，项目真实可用完成度通常不得超过 30：

- 核心语音/聊天/工作流默认走 mock。
- 大部分功能按钮只打开面板、显示日志或提示“即将上线”。
- E2E 测试没有测试真实 server。
- 真实外部依赖未配置，且系统仍显示 available/success。
- 用户主流程不能稳定得到结果。

出现以下任一情况，相关功能不得超过 15：

- `return { info: '待实现' }`
- `return Buffer.from('')`
- 固定假数据冒充实时结果。
- catch 后吞错误并返回成功。
- 前端仅本地状态变化，没有真实 API。

## 必跑命令建议

```powershell
pnpm build
pnpm lint
pnpm --filter @xiaomeng/backend test
pnpm verify
rg "mock|stub|dummy|placeholder|TODO|FIXME|待实现|暂时|即将上线|模拟|return Buffer\.from\(''\)" packages\backend\src packages\frontend\src -n
rg "fetch\(|axios|/api/|WebSocket|socket\.on|socket\.emit" packages\frontend\src -n
rg "success: true|status: 'completed'|ok: true|res\.json|return \{.*completed" packages\backend\src -n
```

这些命令只是入口。评分必须继续追代码路径，不能只看命令是否通过。

## 评分报告格式

每次输出完成度时必须包含：

1. **最终分数**
   - 示例：`真实可用完成度：22/100`

2. **评分口径**
   - 明确是否允许 mock。
   - 明确是否实际启动服务/点击 UI。

3. **证据表**
   - 每个重大扣分项必须带文件和行号。

4. **模块分数**
   - 至少覆盖：聊天、语音、工作区、工具、测试、部署。

5. **最高优先级修复项**
   - 不超过 5 项。
   - 按“修完后分数提升最大”排序。

## 后续改进验收门槛

项目想从 20 分段提升到 50 分段，至少要完成：

- 去掉核心路径默认 mock，外部依赖缺失时显示不可用。
- 把假 E2E 改成真实 server E2E。
- 每个前端入口有明确 API、结果回显和错误回显。
- 工作区工具至少完成 3 个真实高频动作。
- 删除或隔离“待实现”功能入口，避免用户误点。

项目想从 50 分段提升到 75 分段，至少要完成：

- 聊天、TTS、文件生成、工作任务四条主链路真实闭环。
- Docker/PM2/dev/prod 启动路径一致。
- 关键外部依赖有健康检查和 UI 状态。
- 有真实浏览器端验收脚本或手动验收记录。
